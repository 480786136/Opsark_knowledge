核心业务闭环已具备，不需要重建上传、整理、审核和发布。当前适合受控试用，但还不能据此认定达到商业生产放行：主要差距在检索相关性、无答案判断、实际环境元数据、真实 AI 提炼质量，以及目标部署环境验收。

### 检索质量：找对文档不等于拿到答案

原始结果见 [JSON 基线](../knowledge_packs/ops_starter_v1/baseline-2026-10-02.json)。使用原始切片名次，不先去重再抬高排名。

| 指标 | 实测 |
| --- | --- |
| 正向问题 Top-1 文档命中 | 40/42，95.24% |
| 正向问题 Top-5 文档命中 | 41/42，97.62% |
| MRR@5 | 0.9583 |
| 目标文档片段中的预设检查标记覆盖 | 31/42，73.81% |
| 纯库外问题仍返回内容 | 4/6，66.67% |
| 不匹配路径/软件过滤 | 2/2 返回空 |

检查标记覆盖只是答案段落的近似观测，不是语义正确率。有些提问需要解释而不是命令，仍需人工逐条评审。50 个问题样本很小，不能外推为所有真实任务质量。

具体失败包括：

- “MySQL 主从复制延迟如何修复”：没有 MySQL 专题，却返回 Nginx、Redis 等片段。
- “Prometheus 配置告警规则需要什么步骤”：返回 Nginx 配置知识；通用词“配置”不足以证明相关性。
- “nginx -t 成功能说明上游服务正常吗”：前 5 条被上游超时知识占据，没有命中预期配置检查文档。
- 多个问题前 5 条来自同一文档；标题对每个切片都加分，可能挤掉包含检查命令的段落。

本机进程内小样本 p50 6.24 ms、p95 7.61 ms，不含网络、真实模型和并发负载，不能作为生产 SLA。同分排序受切片 ID 影响，后续应增加可解释且稳定的排序规则。

## 建议实施顺序与验收标准

### P0：先把知识用对

1. **无答案和弱相关判断。** 区分未命中、弱相关、可引用，不仅判断关键词分数是否大于零。产品实体冲突、错误码与路径应参与相关性判断，不能单凭通用词命中。
2. **回答段落排序与去重。** 控制每篇文档返回切片数，做段落相关性排序与必要的相邻段补充；保留版本/行号和字符预算。不能简单全局去重而丢失必要证据。
3. **环境和版本适用性。** 审核页展示缺项，支持明确的“通用/未知”；Core 只传递已确认上下文。未知元数据不能当作已验证适用，也不能伪填版本。
4. **AI 提炼失败与质量门禁。** 展示失败 claim、引用位置和原因；保留规则草稿。设置修复重试次数、费用/超时上限和人工入口，不放宽事实证据校验换取表面成功率。

建议扩大至至少 200 条人工标注问题，其中至少 50 条无答案/易混淆问题，并加入真实脱敏任务。初步目标：Top-5 文档命中不低于 95%、人工确认的可回答段落覆盖不低于 90%、无答案误召回不高于 5%。这是建议门槛，不是已实现承诺；危险操作的错误适用性和虚构执行事实必须单独零容忍审核。

真实 AI 验收先选至少 20 条已批准外发的任务，覆盖成功、失败、未执行、证据不足、矛盾证据和恶意资料，人工核对“事实/建议/验收要求”。本轮没有把本机历史资料发送给供应商。

### P1：扩大覆盖并建立维护闭环

- 批量 Markdown/文本/JSON 接入：预览、编码/大小限制、去重、来源与许可、按批次撤回；PDF/Office 按需求再加解析和沙箱边界。
- 知识治理：维护人、来源、适用版本、复核时间、过期提醒、近重复和矛盾知识标记。
- 使用反馈：脱敏查询、无命中/弱相关率、引用采用/否定、用户纠正和关联版本；不记录凭据与原始敏感输入。
- 固定问题集对比关键词与真实 Embedding/融合/重排的效果；“开向量”本身不是质量保证。

### P1：生产放行与故障演练

- `/health/ready` 只探测部分表/列，应补完整 schema head 检查；升级缺失时尽早清晰失败，避免再次以列表 500 暴露。
- API 就绪、Worker 可处理、模型可用和检索降级分开观察；增加积压、失败率、索引耗时、模型成本和检索延迟告警。
- 在目标 PostgreSQL/容器/TLS 环境重跑并发、断网、限流、超时、Worker 中断、升级和备份恢复。按实际业务定义容量、RPO/RTO 与回滚演练。
- 发布前执行真实桌面 Core → 上传 → 整理 → 审核 → 检索 → 引用 → 下架；脚本/mock 测试不能替代桌面密钥存储和现场网络验证。

### P2：需求出现后再做

大规模向量近似索引、共享限流、多副本和跨任务知识合并按容量或业务证据推进。多人授权与空间隔离保持在当前范围之外。
