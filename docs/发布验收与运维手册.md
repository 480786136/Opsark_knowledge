# 单管理员发布验收与运维手册

适用范围：一个管理员、一套独立 Knowledge 服务、一个 API 进程与持久化 Worker。
功能完成、自动验收通过和生产放行分别记录；本手册不会把未运行的测试标成通过。
当前版本的现场实测结果见 [本机流程验收报告](本机流程验收报告.md)。

## 可重复验收

工作区测试资产统一归档到 [知识库测试目录](../../docs/测试/知识库测试/README.md)，按日期与内容保留脚本快照、测试方法和记录。日常 SQLite/页面/检索回归建议使用其中的 `run_tests.py` 入口；以下工程命令保留用于独立仓库、CI 和明确授权的专项验收。历史报告不能替代当前版本重跑。

在项目根目录执行，先安装固定依赖并构建管理页面：

```sh
python -m pip install -c constraints.txt -e '.[test]'
python -m pytest -q tests scripts/test_replay_core_logs.py
python -m ruff check --select E9,F63,F7,F82 knowledge migrations tests scripts
npm --prefix web ci
npm --prefix web run build
python scripts/smoke_workflow.py
```

`smoke_workflow.py` 自动建立新的私有临时目录、SQLite 数据库、API、Worker，以及仅监听
127.0.0.1 的模型和 Embedding mock。它通过正常 HTTP API 上传、提炼、审核发布和检索，
验证草稿隔离、幂等、Worker 重启、来源修订、引用行号、版本切换、下架删除和 Embedding
故障降级。使用在线数据库备份后，另启一个 API 验证恢复后的引用与原版本逐字段一致。
不会读取项目 `.env`，不会调用真实模型，也不会修改业务数据库。失败返回非零退出码。

日志与数据库留在输出中的 `artifact_directory` 私有系统临时目录，便于定位失败。
目录可能含脱敏后来源内容，不应放入 Git、工单或 CI 附件；只分享 `report.json` 的计数和检查结果。
测试进程结束时自动停止。临时测试资料按本机保留策略清理。

浏览器测试另执行：

```sh
cd web
npx playwright install chromium
npm test
```

浏览器测试是否使用真实后端，以测试本身为准；接口 mock 的页面测试不替代上述真实进程验收。
另在项目根目录执行 `python scripts/smoke_browser.py`，会自动启动隔离 API/Worker、建立临时管理员和
来源草稿，通过浏览器真实登录、编辑发布、检索引用与下架。它使用已经构建的 `web/dist`，
不调用模型，凭据只通过子进程环境变量传递，结束自动停止服务。

## 本机 Core 日志回放

默认只读取 Tauri 应用标识 `com.opsark.desktop` 对应目录下的任务事件及归档证据，不读取
模型调用日志、密钥库、终端快照或其他应用目录。macOS 默认目录是
`~/Library/Application Support/com.opsark.desktop`；其他目录可明确用 `--core-data` 指定。

```sh
# 无写入：仅检查计数、关联、SHA-256 完整性与公共上传协议
python scripts/replay_core_logs.py

# 显式选择真实历史日志，在新的隔离服务中进行完整流程测试
python scripts/smoke_workflow.py --with-core-logs --limit 8

# 可选：把脱敏样本写入一个新建的私有临时目录，便于本机人工审核
python scripts/replay_core_logs.py --write-fixtures
```

如果需要上传到已经启动的本机测试服务，先在管理页面创建专用测试库和限定该库的 Key，
通过终端环境变量提供 Key（避免写入命令历史），再显式执行：

```sh
python scripts/replay_core_logs.py --upload --endpoint http://127.0.0.1:8002 \
  --knowledge-base-id TEST_BASE_ID
```

上述操作需要 `REPLAY_KNOWLEDGE_KEY` 环境变量。上传脚本拒绝远端地址和重定向，不会自动发布。
若该测试服务配置了自动 AI 提炼，需先把该服务的 AI 关闭或指向本机 mock，避免来源被转发给供应商；
优先使用 `smoke_workflow.py --with-core-logs`，它会自行隔离供应商配置。

归档证据没有完整的 Core typed execution result，因此此适配器始终标记整体 `partial`、
执行/校验状态 `unknown`，不会根据终端中的 `success` 字样推断任务成功。它保留原始采集不完整与
回放节选标记。回放适配器验证历史资料接入能力，不代表 Core UI 的上传构造器已被端到端测试。
发布前仍须核对对应来源、环境、证据和结论；自动脱敏规则不能替代人工对外发内容的审核。

## PostgreSQL 与 pgvector 验收

生产候选部署使用 PostgreSQL 17 + pgvector。CI 使用带版本的
`pgvector/pgvector:0.8.2-pg17`，正式部署进一步固定审核过的镜像 digest。
独立测试实例上的管理员 URL 放在 `SMOKE_PG_ADMIN_URL` 环境变量中，例如
`postgresql://test_admin:…@127.0.0.1:PORT/postgres`。脚本只在 loopback 上建立随机命名的
`opsark_smoke_*` 和 `opsark_restore_*` 数据库；结束后删除这两个测试库，不迁移 URL 中原来的数据库。
账号必须具有创建数据库和创建 vector 扩展的权限，PATH 中的 pg_dump/pg_restore 版本不得低于服务器。

```sh
python scripts/smoke_workflow.py --postgres-admin-url-env SMOKE_PG_ADMIN_URL
python scripts/smoke_workflow.py --postgres-admin-url-env SMOKE_PG_ADMIN_URL --with-core-logs
python scripts/benchmark_retrieval.py --postgres-admin-url-env SMOKE_PG_ADMIN_URL --documents 500 --queries 200
```

性能脚本通过 HTTP 建立 500–1000 个合成文档并由 4 个 Worker 完成发布，验证中文主题、错误编号、路径、
无匹配、环境与软件版本过滤、只检索当前版本、下架和输出预算，再使用 10 个独立客户端执行检索。
输出 p50/p95/p99、吞吐、错误数和预期文档命中数；脚本不开模型/Embedding，测量的是 PostgreSQL 关键词路径。
这组本机合成基线不能替代客户实际语料、向量供应商延迟或正式部署环境的 SLA。

## 部署和升级

1. 保存准备发布的代码版本、依赖锁定文件、镜像 digest 和配置清单；配置清单不包含明文凭据。
2. 为目标数据库做完整备份并在新库恢复验证。升级失败时使用旧应用镜像和已验证的备份恢复，不能仅降级 ORM。
3. 在 Compose 环境中设置强随机 `KNOWLEDGE_DB_PASSWORD`（至少 32 个 URL-safe 字母数字字符，避免 URL 保留符）；可选的服务器集成 Token 保持至少 32 字符，
   不配置服务器集成时留空。初始化管理员使用交互式 bootstrap，不在启动命令中写密码。
4. 执行 `docker compose config --quiet`、`docker compose build`、`docker compose up -d`。
   API 启动先执行 `alembic upgrade head`，Compose 使用 `/health/ready` 检查数据库/关键表就绪，Worker 等 API 就绪再启动。
5. 首次执行 `docker compose exec api python -m knowledge.bootstrap`。访问管理页完成一次测试库的
   上传、审核发布、检索、下架；确认 Worker 的任务状态最终到达 `done`。
6. 检查容器重启、磁盘容量、队列积压、失败任务、管理员登录、Key 撤销、来源删除及备份恢复。

Compose API 默认只绑定主机 127.0.0.1:8002；正式远端访问由反向代理提供 TLS，限制管理入口来源，
并设置 `COOKIE_SECURE=true` 和精确的 `ALLOWED_ORIGINS`。不要把服务 Token 放进前端配置。
API/Worker 使用非 root 用户、只读根文件系统，运行日志写入单独的 `knowledge-runtime` 数据卷。
数据库不映射宿主端口。当前进程内限流要求单 API 进程，不能直接水平扩容成多个 API 副本。

## 备份与恢复

应备份 PostgreSQL 数据库以及受保护的部署配置/凭据。数据库保存来源、草稿、发布版本、索引、
管理员、Key 哈希及审计；私密原始资料仍可能存在于历史备份，需要给备份本身设置访问控制与保留期。
停止 Worker 不是在线 pg_dump 的必要条件；恢复切换前必须停止业务写入，避免丢失备份之后的新数据。

在受保护的备份目录执行，文件权限设为仅当前维护者可读：

```sh
umask 077
docker compose exec -T db pg_dump -U knowledge -d knowledge --format=custom --no-owner > knowledge.dump
docker compose exec -T db createdb -U knowledge knowledge_restore_check
docker compose exec -T db pg_restore -U knowledge -d knowledge_restore_check --no-owner --exit-on-error < knowledge.dump
```

恢复检验库命名必须先确认不存在；不能覆盖已有库。另起隔离 API 指向恢复库，核对管理员访问、库/来源/
文档/版本/任务数量、样本引用内容和检索命中；记录备份时间、恢复耗时、可恢复点以及差异。
恢复演练完成后由维护者按确认的具体库名清理演练库。禁止在生产卷执行 `docker compose down -v`。

本地 SQLite 备份必须用 sqlite3 backup API 或在服务完全停止后同时妥善处理 WAL，不能只复制正在写入的
`.db` 文件；可参考 smoke 脚本里的 `backup_restore()`。这是开发/小规模单机恢复方式，生产主路径为 PostgreSQL。

## 发布放行条件

- 固定提交的后端回归、迁移、真实 API/Worker smoke、前端构建与浏览器测试全部通过。
- PostgreSQL/pgvector 上重复同一流程，向量故障能降级，索引失败保留旧发布，重试能恢复。
- 真实 Core UI 上传与 Agent 检索各完成至少一次联调；历史归档适配器回放不能替代这两个入口。
- 真实提炼供应商使用已批准的脱敏样本，人工核对至少 20 个不同任务的适用条件、失败边界、引用正确性；
  mock 测试只证明协议与异常路径，不证明模型知识质量。
- 按预计库规模和并发执行检索压测，记录 p50/p95/p99、错误率、候选量、队列延迟和资源占用；
  由业务确认可接受指标。超出当前容量上限时必须缩小库或扩展检索实现后重新验收。
- 在目标部署环境完成容器重启、磁盘不足处理、TLS/cookie 配置和备份恢复演练，明确责任人与备份保留期。

任何未完成项都保留为上线门禁。单管理员范围内的可商用评估，不包括公众注册、多用户隔离、跨租户服务、
长期记忆或 PDF/OCR 导入能力。
